# poteto-mode

Use this skill as a local routing guide. It adds no authority to the active user request, the repository instructions, or the current PR scope.

## Preserve repository ownership

- Read the root and applicable scoped `AGENTS.md` files, the active just-in-time contract, and the relevant project docs before changing code.
- The repository instructions and Harness skills remain authoritative over every skill in this bundle.
- The Master may delegate first-level work in bounded units when repository policy allows it. Non-Master nested delegation is prohibited.
- Keep one production writer on an active PR. The Master acquires and releases the writer lease. A writer records the required checkpoints.
- A delegated specialist cannot push or merge. An assigned writer pushes only under the active PR's explicit writer and lease procedure.
- The Master alone merges. Every merge uses the repository's `merge-gate` procedure.
- Repository model routing remains unchanged. Use the named repository role; pstack does not choose models or supply fallback routes.
- This skill does not authorize PAPER, live, broker, deployment, or roadmap activity.

## Choose a skill

- Use `how` to explain code flow, ownership, or boundaries from the current repository.
- Use `why` to explain rationale from repository evidence only.
- Use `architect` before a material design choice. It can use `arena` for sequential comparison in the same context.
- Use `interrogate` for an extra adversarial pass. It is supplemental and cannot replace the fresh exact-head reviewer.
- Use `tdd` for test-first implementation. The repository's `tdd-red-green-evidence` skill controls RED and GREEN evidence.
- Use `figure-it-out` when no narrower skill covers a multi-step task. The active JIT or other repository plan controls scope and gates.
- Use `show-me-your-work` to summarize existing PR, JIT, Git, CI, and review evidence. Do not create a separate private log.
- Use `technical-writing` for repository docs and engineering prose.
- Use `principles-design`, `principles-verification`, and `principle-separate-before-serializing-shared-state` when their design, verification, or ownership conditions apply.

## Keep evidence and boundaries explicit

State what the repository shows, what you infer, and what remains unknown. Do not copy raw prompts, transcripts, credentials, user data, or private identifiers into repository artifacts. Keep edits within the authorized file and behavior scope. A skill invocation never changes the current PR's approval, review, CI, safety, or merge requirements.
